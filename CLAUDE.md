## Commands

```bash
npm run dev              # start dev server (Turbopack)
npm run build             # production build (also runs the TypeScript check)
npm start                 # serve the build from `npm run build` (production mode) — for *-prod.mjs scripts below
npm run lint               # ESLint (flat config, eslint.config.mjs)
npm run locations:import:kocaeli   # fetch+filter OSM/Overpass candidates for one province
npm run locations:verify           # polygon-verify, dedupe, score candidates -> data/locations/*.json
npm run locations:report           # print a verification summary from data/locations/*.json
npm run locations:test-filter      # unit-test the Overpass candidate filter logic
npm run test:photo-feature   # pure-logic tests for app/_lib/photo-validation.ts, no server needed
npm run test:photo-api       # E2E test of the /api/job-photos/process route against a running dev server
npm run test:photo-browser   # Playwright E2E for the photo-upload UI, against a running dev server
npm run test:regression      # Playwright smoke test that unrelated flows still work, against a running dev server
npm run test:location-system # Playwright E2E for the İl/İlçe/Bölge-Tesis picker (job-location.ts), against a running dev server
```

There is no Jest/Vitest — "tests" are plain Node scripts under `scripts/`, run directly (`node scripts/....mjs`), not through a runner. Two kinds:
- **Pure-logic** (`test-photo-feature.mjs`, `locations/test-filter.mjs`): import the `.ts` module directly using Node's built-in TypeScript support, no server needed.
- **Browser/E2E** (`test-photo-api.mjs`, `browser-test-*.mjs`): require `npm run dev` already running on `localhost:3000` first (`test-photo-api.mjs` hits the route with `fetch`; the `browser-test-*.mjs` ones drive real Chromium via Playwright). `test:photo-browser` needs fixture images from `node scripts/generate-photo-test-fixtures.mjs` first.

Treat `npm run lint` + `npm run build` as the baseline correctness gate for app code; use the scripts above (or a throwaway `node -e "..."`) to independently cross-check pure logic (money parsing, phone normalization, geo functions, photo validation) before trusting it.

`scripts/tmp-*.mjs` (e.g. `tmp-completion-flow-test.mjs`, `tmp-withdraw-offer-test.mjs`) are one-off Playwright verification scripts written alongside a specific feature commit and left committed afterward as a record — they are not npm scripts and aren't meant to be maintained as a regression suite. Follow the same pattern for a new feature (`tmp-<feature>-test.mjs`, requires `npm run dev` running) rather than editing an old one to test something unrelated. A `-prod` suffix (e.g. `tmp-verify-provider-profile-prod.mjs`, `tmp-production-mode-route-audit-test.mjs`) marks the same kind of script pointed at a **production build** (`npm run build && npm start`, not `npm run dev`) instead of dev — used to catch things dev mode can't (the `NODE_ENV === "development"` dev-seed-account gate being off, real minified bundle/chunk 404s, etc.); these register fresh accounts through the real Kayıt Ol flow rather than relying on `DEV_ACCOUNTS`; there are already over a dozen of these, so add a new `-prod` script rather than trying to parameterize an existing dev-mode one.

## Architecture

**Stack:** Next.js 16 (App Router, Turbopack), TypeScript, React 19, Tailwind CSS v4. No auth provider, no persistent server-side state for the actual app — nearly everything is client-side `localStorage`, written as typed data-layer modules under `app/_lib/`. There are two Route Handlers: `app/api/job-photos/process/route.ts` (stateless image processing that can't run in the browser; see "Photo upload pipeline" below) and `app/api/health/route.ts` (a DB connectivity check — see "Database scaffold" below). Both are the only server-side code in the app; every feature (`users`, `job-store`, `offers`, `session`, `notifications`, ...) still reads/writes `localStorage` exclusively. `tsconfig.json` defines a `@/*` path alias but nothing actually imports through it — every real import in the codebase is relative (`../_lib/...`, `./...`); match that convention rather than introducing `@/`-style imports.

### Directory roles

- `app/_components/` — UI components (route-excluded via the `_` prefix). Presentational components have no hooks; anything reading session/localStorage is a `"use client"` component.
- `app/_lib/` — the entire data/business layer: localStorage-backed "tables" (`session.ts`, `users.ts`, `job-store.ts`, `offers.ts`), an IndexedDB blob store (`photo-blob-store.ts`), pure validation modules (`*-form-validation.ts`, `money.ts`, `phone.ts`, `password-rules.ts`, `photo-validation.ts`), a shared cross-source lookup (`jobs-lookup.ts`), and reactive hooks (`use-*.ts`). Five of the `use-*.ts` hooks are reusable UI-interaction primitives rather than data hooks — reuse them instead of reimplementing the same behavior locally: `use-dismiss-animation.ts` (measure element height → animate slide+fade+collapse → invoke a callback only after the animation completes, skipped entirely under `prefers-reduced-motion`; used by the notification list), `use-scroll-lock.ts` (iOS/Android-safe body scroll lock via `position: fixed` + scroll-offset restore, not plain `overflow: hidden`; used by the mobile nav menu), `use-dropdown.ts` (open/close state + outside-click/Escape-to-close, with an `extraRefs` escape hatch for portal-rendered content that `Node.contains()` would otherwise see as "outside"; used by the mobile menu and profile/notification dropdowns), `use-auto-dismiss-banner.ts` (time-triggered, not user-triggered: shows a standalone banner for a fixed duration then fades it out — deliberately separate from `use-dismiss-animation.ts`'s click-triggered slide+collapse; used by the job-requests panel's delete confirmation banner), and `use-media-query.ts` (a `matchMedia`-backed `useSyncExternalStore` hook for responsive JS branching — see "Provider job listing" below for why this is safe from hydration mismatches here but wouldn't necessarily be elsewhere).
- `app/api/job-photos/process/` — `runtime = "nodejs"` (needs `sharp`'s native bindings, won't run on Edge). Stateless request-in/image-out; writes nothing server-side.
- `app/_data/turkey/` — static reference JSON for provinces and districts only (`provinces.json`, `districts.json`, complete for all 81 provinces), bundled into the app at build time. Facility data (OSB/port/free-zone/etc.) does **not** live here — see "Turkey location data" below.
- `data/` (repo root, **not** under `app/`) — output of the location-verification pipeline: `data/locations/locations.json` (the single facility dataset), `data/locations/location_suggestions.json`, `data/locations/location_manual_overrides.json`, `data/locations/raw/*.json` (per-province Overpass fetch cache), and `data/boundaries/*.geojson` (district polygons, currently only Kocaeli). Read by `app/_lib/turkey-locations.ts` via a relative import; regenerated by the scripts below, not hand-edited.
- `scripts/locations/` — standalone Node ESM (`.mjs`, no TypeScript, no ts-node) CLI pipeline: Overpass API fetch → district-polygon verification → dedup → confidence scoring → writes to `data/locations/`. Not part of the Next.js build; run manually via the `locations:*` npm scripts. `migrate-legacy.mjs` is a one-off (already-run) script, not an npm script — see "Turkey location data" below.

### No real backend: what that means in practice

- "Tables" are localStorage-backed modules, not a database. Reads/writes go through a cache-plus-`useSyncExternalStore` pattern (see `session.ts`, `job-store.ts`, `offers.ts`): a module-level cache compares the raw localStorage string to avoid returning new object references on every render, `getServerSnapshot` always returns `null`/`[]` for SSR safety, and writes call an internal `notify()` so every subscribed component re-renders.
- **Do not use `useEffect` + `setState` to read localStorage on mount** — the project's ESLint config enforces `react-hooks/set-state-in-effect` and will fail lint on that pattern. Use the existing `useSyncExternalStore`-based hooks (`use-session.ts`, `use-jobs.ts`, `use-offers.ts`) or extend that pattern for new localStorage-derived state.
- **Writes must not silently claim success.** `local-storage.ts#writeJson` wraps `localStorage.setItem` in try/catch, logs the real error via `console.error`, and returns a `boolean` (not `void`) — `false` on failure, with the module-level cache/`notify()` left untouched so subscribers keep seeing the last-known-good data instead of a phantom update. Every table's internal write wrapper (`job-store.ts#writeUserCreatedJobs`, `offers.ts#writeAllOffers`, `users.ts#writeUsers`, `session.ts#setSession`/`clearSession`, `notification-reads.ts`/`notification-dismissals.ts#writeIds`) propagates that boolean, and every public mutation (`createJob`, `updateJob`, `createOffer`, `updateOfferStatus`, `registerUser`, ...) checks it and returns `{ ok: false, error: STORAGE_WRITE_ERROR_MESSAGE }` (the one shared, non-technical error string, exported from `local-storage.ts`) instead of the normal success value when the underlying write actually failed — never `console.error`-and-continue. Side effects that depend on a write succeeding (deleting an old photo blob, deleting a stale logo blob) are ordered *after* the guarded write, not before, so a failed write can never leave a dangling reference to an already-deleted blob (see `job-store.ts#deleteJobPhoto`'s write-then-delete order). `deleteJobWithOffers` is the one deliberate exception: its secondary `offers` write (flipping sibling `pending` offers to `rejected`) is best-effort after the primary job deletion already succeeded — a failure there is logged, not surfaced as an overall failure, since unwinding an already-successful deletion would need real rollback machinery this codebase doesn't have.
- Passwords (`app/_lib/users.ts`) are hashed with unsalted SHA-256 via the browser's `crypto.subtle` — explicitly documented in that file as a dev-only stand-in, not production-grade auth.
- Five dev-only seed accounts (Zeynep/hizmet-alan, Mert/hizmet-veren, Mehmet Demir/hizmet-veren, "Nakliye Demo"/hizmet-veren, "Admin Kullanıcı"/admin — see `DEV_ACCOUNTS` in `users.ts`) are created by `seedDevAccountsIfNeeded()`, called from `login-form.tsx`. The gate is an allow-list, `NODE_ENV === "development"` (not a `!== "production"` block-list) specifically so it stays off under `next build && next start`, including Vercel preview/production. The last two exist solely to exercise the provider-document-verification feature (below) without manual setup: `seedNakliyeciProviderProfileIfNeeded()` runs after the main upsert loop and additionally seeds the Nakliyeci account's `provider-services.ts` row (Nakliye only), a demo document (auto-approved, `reviewedByAdminId` pointing at the seeded admin), and its declaration consent — none of which `upsertDevAccount` itself knows about, since those three tables live outside `StoredUser`. `admin` is otherwise unreachable: it is never a selectable "Hesap Türü" in the registration form (`types.ts#UserRole`'s third value), so the dev seed is its only creation path.
- Authorization checks (role checks, ownership checks, offer-status transitions) are implemented once in the `_lib` data-layer functions (e.g. `offers.ts#createOffer`/`updateOfferStatus`) and called from UI — never re-implemented ad hoc in a component. `contact-access.ts#getRevealedContactForOffer` is the single gate for revealing a counterparty's phone/email (only when an offer is `accepted` and the caller is a party to it); nothing else should read raw phone/email off a `StoredUser`. `job-requests.ts#canViewJobAddress` is the parallel gate for `Job.addressText` — same `ENGAGED_OFFER_STATUSES` timing, but deliberately a separate function (not folded into `contact-access.ts`, which stays scoped to phone/email) with one extra exception: the job's own owner always sees it, regardless of offer status.
- The `/api/job-photos/process` route reads a client-supplied `role` field to gate uploads to `hizmet-alan` — this is defense in depth, not the authorization boundary. Since there's no real session on the server, a forged request could send any role; the actual authority check happens again server-side-equivalent in `job-store.ts#createJob`/`deleteJobPhoto` (the localStorage write path), which is what a spoofed request can't bypass.
- `reset-demo-data.ts` + `app/gelistirme/demo-veri-sifirla` (`notFound()` unless `NODE_ENV === "development"`) is a dev-only tool to wipe transactional data (jobs/offers/ratings/notification read+dismiss state/recently-viewed) belonging to the seed accounts (`DEV_ACCOUNT_EMAILS`) without touching the seed accounts themselves — a job counts as the seed account's if `requesterId` matches, an offer/rating if either it belongs to such a job *or* its `providerId`/`(rater/provider)Id` is a seed account (so a seed provider's offer on a *real* user's job is removed without touching that job or its other offers). There's no separate "operation" record to clean up (`Job.operationId` is just a field — deleting a seed account's jobs, including every sibling in a multi-service operation, already covers it) and no separate notification table either (`notifications.ts` derives them live, so they disappear once the underlying jobs/offers do — `DemoDataCounts#demoNotificationCount` only exists to *report* that, via the real `getNotificationsForSession`, not to delete anything). It has a manual dry-run-then-apply mode (`planDemoDataReset()` / `executeDemoDataReset()`, used by that page) and a one-time auto-migration (`runDemoDataResetMigrationIfNeeded()`) gated by a `localStorage` version flag — bump `DEMO_DATA_RESET_VERSION` to make it re-run once in browsers that already completed an earlier version. Note: `seedDevAccountsIfNeeded()` (below) only ever syncs the 3 accounts themselves — there is no seed for jobs/offers/notifications, so nothing here needs to be "disabled" for a reset to stick.

### Photo upload pipeline

Job photos flow through three layers that only make sense together:

1. **Client-side pre-check** (`photo-validation.ts`): sniffs the real file format from magic bytes (never trusts the extension/declared MIME), enforces size/count limits, and SHA-256-hashes content to reject exact duplicates.
2. **Server-side processing** (`app/api/job-photos/process/route.ts`, Node runtime): re-validates by actually decoding the image with `sharp`. HEIC/HEIF (common from iPhones) can't be decoded by the bundled libvips due to codec licensing, so those go through `heic-convert` (WASM, unrestricted) first. The pipeline then auto-rotates from EXIF orientation and **strips all EXIF/GPS metadata** (no `.withMetadata()` call) before returning JPEG/PNG/WebP bytes.
3. **Client-side storage** (`photo-blob-store.ts`): the processed blob is written to IndexedDB (localStorage's ~5-10MB quota can't hold up to 10 photos × 10MB each). `job-store.ts` only stores a `storageKey` pointing into that blob store on the `Job.photos` record; `use-job-photo-url.ts` resolves a `storageKey` back to a revocable `URL.createObjectURL` for `<img>` rendering.

### Domain model

- Three roles on `types.ts#UserRole`: `hizmet-alan` (service requester, posts `Job`s), `hizmet-veren` (service provider, posts `Offer`s on jobs), and `admin` (internal-only, gates the `/admin` document-review panel — see "Provider document verification" below; never a selectable "Hesap Türü" at registration, created only by the dev seed). Role gating is checked both in UI (which fields/buttons render) and in the data layer (which operations are allowed). Registration (`login-form.tsx` kayıt mode, validated by `register-form-validation.ts`) collects company info for both public roles — `companyName`, `companyType` (`company-type.ts`), `province`/`district`, plus a combined legal-consent checkbox (see "Legal documents" below) — stored directly on `StoredUser` (`users.ts#registerUser`); this is separate from and unrelated to the richer, optional `ProviderProfile` below. **`hizmet-veren` registration takes a different, second code path**: instead of calling `registerUser` directly, `login-form.tsx` calls `provider-registration.ts#registerProviderAccount`, which also collects a service-category selection and 1+ "Faaliyet Belgesi" uploads as part of the same form — see "Provider document verification" below for the full flow; `hizmet-alan` registration is untouched and still calls `registerUser` directly.
- Jobs come from two separate sources merged only through `jobs-lookup.ts#findJobById`: `jobs.ts` is a static in-memory array of seed example listings (`requesterId: null`, not localStorage-backed), while `job-store.ts` is the real localStorage "table" for user-created jobs. Never query `job-store.ts` alone when you need "any job by id" — other modules (`offers.ts`, `contact-access.ts`) go through `jobs-lookup.ts` so seed listings resolve too.
- `Job.requesterId` links a job to the user who created it (`null` for the seeded example listings) — this is what `contact-access.ts` and the notifications system use to determine "is this my job."
- **Job location** is `province`/`district` (always present, real names from `turkey-locations.ts`), `workLocationType` (the Bölge/Tesis display name — either copied from a picked catalog `Facility.name`, or the user's own facility name in `locationMode: "custom"`), `facilityId?` (the picked `Facility.id`; never set in custom mode), `locationMode?` (`"catalog"` | `"custom"`, absent on pre-2026-07-25 jobs and always read as `"catalog"` when absent), `companyOrFactoryName?`, `addressText?`, `neighborhood?`, `locationUrl?`, `directionsNote?` — see "Centralized job location" below for the shared formatter/resolver, the custom-facility flow, and the address privacy gate.
- `Job.operationId?`/`Job.workEndDate?` — see "Çoklu Hizmet Operasyonu" below. Both absent on every job created before this feature (and on any job still created via the single-service path); `workEndDate` pairs with the pre-existing `workDate` to form a date *range* rather than a single day.
- `Job.createdAt?`/`Job.publishEndAt?`/`Job.republishedFromJobId?`/`Job.republishedToJobId?` — see "İlan Yayın Süresi Yönetimi" below for the 14-day listing-expiry/republish system these back.
- `Job.status` (`"yayinda" | "tamamlandi" | "iptal"`) never changes after creation for a real user's job — `createJob` always writes `"yayinda"`, and no other function (including `updateJob`) touches it. Time-varying state (in-progress, tamamlandı, etc.) is derived at read-time from the job's `Offer`s via helpers in `job-requests.ts` (`getJobRequestFilter`, `getJobAvailabilityForProvider`, `isJobEditable`) — check that file, not `Job.status`, when you need a job's effective state. `getJobOfferAvailability` returns `"acik"` for a `"yayinda"` job as long as its settled offer (if any) is at most `"accepted"` — see "New offers vs. accepted vs. work started" below for exactly where it flips to `"kapali"`, since `Job.status` itself never does. `jobHasAcceptedOffer` still exists but its only remaining caller is `offers.ts#deleteJobWithOffers`'s "can't delete a job with an active/completed offer" guard — it is deliberately **not** used for offer-acceptance/visibility gating anymore.
- **Job editing** is gated by `job-requests.ts#isJobEditable`/`JOB_NOT_EDITABLE_MESSAGE` (the offer process having started — any offer in `ENGAGED_OFFER_STATUSES` ∪ `completed` ∪ `cancelled` — permanently locks a job from further edits) — the single source of truth called from three independent layers that must stay in sync: the "İlanı Düzenle" link's visibility (`job-requests-panel.tsx`), the edit route's own guard (`job-edit-form.tsx`), and the data-layer write (`job-store.ts#updateJob`, which takes the current `Offer[]` as a parameter precisely so it can re-check this without importing `offers.ts` — that would be circular, since `offers.ts` already imports `job-store.ts`).
- `Offer.status`: `pending -> accepted | rejected` via `offers.ts#updateOfferStatus` (job-owner/requester only). An `accepted` offer can further move to `in_progress` via `offers.ts#startWorkForOffer`, or to `agreement_failed` via `offers.ts#recordAgreementFailure` (both requester-only, both leave `Job.status` untouched). `agreement_failed` is deliberately excluded from `ENGAGED_OFFER_STATUSES`/`jobHasAcceptedOffer`, which is what lets the job be deleted afterward (`deleteJobWithOffers` only blocks deletion on an active/completed offer) and frees the provider's capacity slot — it does *not* gate re-offering, since new offers were never blocked in the first place (see "Single active acceptance" below). A `pending` offer can also move sideways to `withdrawn` via `offers.ts#withdrawOffer` (provider-only) — deliberately excluded from `ENGAGED_OFFER_STATUSES` too, since a never-accepted offer never held capacity or contact access.
- **Single active acceptance per job**: a job can receive `pending` offers from multiple providers concurrently, but at most one may ever be settled (accepted or further along) at a time — enforced by `job-requests.ts#isOfferPendingActionBlocked` (built on `getSettledOfferForJob`, which unions `getEngagedOfferForJob` and `getCompletedOfferForJob` — the single shared source of truth), called from *both* `offers.ts#updateOfferStatus` (rejects a second accept/reject attempt at the data layer, immune to a stale tab or a bypassed button) and `incoming-offer-card.tsx` (swaps the Kabul Et/Reddet buttons for a fixed notice, `job-requests.ts#OFFER_PENDING_BLOCKED_MESSAGE`). This fires as soon as **any** offer is `accepted` — before work starts — and deliberately does **not** mutate sibling offers to `rejected`: they stay `pending` untouched, so if the settled offer later fails out to `agreement_failed` they become actionable again automatically (purely derived, no extra write); once the settled offer instead progresses *past* `accepted` (work actually starts), those siblings surface as closed in the provider's own tabs instead — see "Provider offer tabs" below. This accept/reject-action lock is a **separate, earlier** threshold than whether the job still accepts brand-new competing offers — see next.
- **New offers vs. accepted vs. work started.** `job-requests.ts#isJobClosedToNewOffers(jobId, offers)` is the single source of truth for "can anyone else still submit a competing offer on this job" — built on the same `getSettledOfferForJob`, but only `true` once the settled offer is *past* `"accepted"` (`in_progress`/`completion_requested`/`completion_disputed`/`completed`). An `accepted`-but-not-started offer deliberately does **not** close the job — it's a pre-work-start negotiation stage, so other providers can still freely submit competing `pending` offers. Three call sites share this one check and must never drift apart: `offers.ts#createOffer` (data-layer authority), `offers.ts#canProviderSubmitNewOffer` (what `offer-panel.tsx` renders — the form is replaced by "Bu ilan için bir hizmet verenle iş başlamış." once it flips — and what the "Operasyondaki Hizmetler" card's own "Teklif Ver" link checks, see "Operation discovery & status UI" below), and `getJobOfferAvailability` (feeds its `"kapali"` value — previously a dead branch, since `Job.status` never changes, now live). Because all three read the same function, a "Teklif Ver" button that's visible always corresponds to a real, submittable offer form on that job's own page.
- **Provider offer tabs ("Verdiğim Teklifler")**: `job-requests.ts#getProviderOfferFilter(offer, offers)` — note it takes the *full* offers array, not just the caller's own, because it needs sibling context — is the single source of truth for which of the four `my-offers-panel.tsx` tabs (Aktif/Devam Eden/Tamamlanan/Kapanan Teklifler) an offer appears in, and `getProviderOfferNotificationHref`/`getProviderOffersTabHref` build every Hizmet Veren notification's `href` from that same function, so a notification always lands on the tab the offer actually renders in (never a hand-rolled route string). "Kapanan Teklifler" bundles three unrelated reasons an offer is permanently non-actionable: (1) a still-`pending` sibling offer on a job where a *different* offer has progressed past `accepted` (`isOfferClosedByJobProgress`, built on `getSettledOfferForJob` rather than a new status) — shown with an overridden "Başka Bir Hizmet Verenle Anlaşıldı" badge and a dedicated notification (see below); (2) `agreement_failed`; (3) `cancelled` (a disputed job resolved as cancelled, shown with an extra "İtiraz sonrası iş iptal edildi." line). (2) and (3) keep their real `getOfferStatusLabel` badge instead of the override. None of the three render any action button in that tab. `getProviderOfferFilter` only recognizes `"devam-eden"`/`"tamamlandi"`/`"kapanan-teklifler"` as explicit `?durum=` values (anything else, including an old/removed tab key, silently falls back to `"aktif"` rather than erroring) — always build a link to this page via `getProviderOffersTabHref(filter)`/`getProviderOfferNotificationHref(offer, offers)` rather than hand-writing a `?durum=...` query string, or it will silently land on the wrong tab.
- **Incoming offers screen ("Gelen Teklifler")** groups a requester's incoming offers into a Hizmet Türü → İlan → Teklifler hierarchy instead of one flat list — `incoming-offer-grouping.ts#groupIncomingOffersByCategoryAndJob(offers, jobById)` builds `IncomingOfferCategoryGroup[]` (each holding nested `IncomingOfferJobGroup[]`), rendered by `incoming-offer-category-section.tsx` (one category box, wrapping the unchanged `incoming-offer-card.tsx` per offer) inside `incoming-offers-panel.tsx`. It's a single, non-sorting pass — a group's position is fixed by wherever its first (already-sorted) offer lands — so callers must pre-sort with `job-requests.ts#sortIncomingOffersForDisplay`, which applies a seven-tier priority (`incomingOfferSortWeight`): `accepted` first, then `pending`, then `in_progress`/completion-in-progress stages, then `completed`, then `agreement_failed`/`cancelled`, then `rejected` — `accepted` was deliberately moved *above* `pending` (previously the reverse) so that accepting an offer never visually demotes it below its still-pending siblings on the same job. It's implemented as a deterministic slot-reordering algorithm rather than a comparator returning `0` across different jobs, specifically to avoid a non-transitive/engine-dependent order when two jobs' offers interleave in the base (recency-sorted) array — see the function's own doc comment for the full reasoning. Visibility is a separate, upstream concern: `job-requests.ts#isOfferShownInIncomingOffersScreen` (its own single source of truth, deliberately kept apart from the broadly-shared `isOfferVisibleInNormalLists`) removes `rejected`/`agreement_failed` offers from this screen entirely — not deleted, not merely reordered, just excluded before grouping — so a job/category with zero remaining visible offers simply never produces a group (no explicit "collapse" step needed), and reappears automatically the moment a new offer arrives for it. An offer whose job can't be resolved (deleted — see "Notifications are derived, not stored" below) lands in a fixed `"İlan Bilgisine Ulaşılamayan Teklifler"` category rather than being dropped. The panel also drops a job's offers entirely once `getJobRequestFilter(job, offers) === "tamamlandi"` (the winning offer has moved to Hizmet Taleplerim's "Tamamlandı" view, and any still-`pending` siblings are no longer meaningful) — deliberately *not* for `"kabul-edildi"`/`"devam-eden"`, since the requester's Kabul Et/Reddet/Tamamlandığını Onayla/İtiraz Et actions for those stages live on this same screen, inside `IncomingOfferCard`. The completion `JobRatingModal` moved out of `incoming-offer-card.tsx`'s own local state and up into `incoming-offers-panel.tsx`, for the same reason and via the same pattern `job-requests-panel.tsx` already uses: the card that triggers the modal can itself unmount (its offer's job-group disappearing from the grouping above) in the same render the offer completes, which would silently close a modal owned by local state before it's ever seen.
- **Completion is a two-party handshake, not a single write.** From `in_progress`, the provider calls `offers.ts#requestCompletion` (-> `completion_requested`, records `completionRequestedByUserId`/`completionRequestedAt`); the requester then either `confirmCompletion` (-> `completed`) or `disputeCompletion` with a 10–1000 char note (-> `completion_disputed`), and a disputed offer is resolved by the requester via `resolveCompletionDispute` to either `completed` or `cancelled`. The party that requested completion is blocked from confirming/disputing their own request. Because there's no server-side scheduler, a `completion_requested` offer that the requester never acts on is auto-approved after `COMPLETION_AUTO_APPROVE_DAYS` (7 days) by `applyExpiredCompletionAutoApprovals()` — this runs lazily (checked from `use-offers.ts` on read, not on a timer) and sets `autoCompleted: true`, which caps the `ratings.ts` review window to `AUTO_COMPLETED_RATING_WINDOW_DAYS` (30 days; manually-confirmed completions have no review deadline). Within `job-requests-panel.tsx`'s "Devam Eden" tab, jobs whose engaged offer is stuck in `completion_requested` are sorted to the top — `job-requests.ts#isOfferAwaitingCompletionConfirmation(engagedOffer)` is the single source of truth (a boolean-only wrapper around that one status, not a new derived state); the tab's sort is a stable `Array.prototype.sort` (stable since ES2019) over just that weight, so entries sharing a weight keep whatever order `myEntries`/`useAllJobs()` already gave them rather than inventing a secondary date comparison. Aktif/Tamamlanan tabs are untouched.
- **Provider capacity**: `provider-capacity.ts#MAX_ACTIVE_JOBS` (5) caps how many jobs a `hizmet-veren` can hold concurrently, counted via `getActiveJobCount`/`hasReachedActiveJobLimit` over `job-requests.ts#ENGAGED_OFFER_STATUSES` (`accepted`, `in_progress`, `completion_requested`, `completion_disputed`) — a completion request or an unresolved dispute still counts against capacity; only a terminal status (`completed`, `cancelled`, `agreement_failed`, `rejected`, `withdrawn`) frees a slot. Enforced at **two** independent points, not just one: `offers.ts#createOffer`/`canProviderSubmitNewOffer` (offer-creation time) and, separately, `updateOfferStatus` when `nextStatus === "accepted"` (accept-time, against a freshly-read offers list) — the second check exists because a provider can hold multiple still-`pending` offers on independent jobs while under capacity, and two different requesters accepting those offers unaware of each other could otherwise push the provider past `MAX_ACTIVE_JOBS`; a rejected accept attempt leaves the offer `pending` and every other record untouched.
- **Ratings** (`ratings.ts`): a requester submits one 1–5 star `Rating` per completed `Offer` for the provider (`submitRating`), aggregated per-provider via `getProviderRatingSummary`. Gated by the auto-completion review window above, not by role/ownership checks alone. `job-rating-modal.tsx` shows the provider's identity next to the star input — logo via `use-job-photo-url.ts` on `providerProfile.logoStorageKey`, falling back to the same initials-avatar pattern used by `profile-info-card.tsx`/`panel-welcome-card.tsx` (`profile.ts#getInitials`), and company name if set else the provider's own name — read straight off `offer.providerId`/`users.ts#findUserById`; the modal only ever receives the single accepted-then-completed offer being rated (from `getCompletedOfferForJob`), so no extra "is this the right offer" check is needed.
- **Provider profiles** (`provider-profile.ts`): an optional `ProviderProfile` (company name, logo, 50–500 char bio, founded year, service regions, expertise, `serviceCategories`, `serviceFeatures`, `experienceRange`) on `StoredUser`, meaningful only for `hizmet-veren`. **`ProviderProfile.expertise`/`serviceCategories` are both deprecated** (per their own doc comments in `types.ts`) now that `provider-services.ts` is the single source of truth for a provider's current service-category selection (see "Provider document verification" below) — `expertise` is still read/written only by the legacy Hesap Ayarları > Firma Profili "Uzmanlık Alanları" chips (`provider-profile-editor.tsx`), and `serviceCategories` is kept only so older stored profiles still parse in `normalizeStoredUser`; new code must never write to either, and `service-catalog.ts#migrateLegacyExpertiseToServiceCategoryIds` is the one-way bridge from the old field to the new table — fully optional and normalized on read like `Job.photos`, so pre-migration users just render blank/`"-"` fields rather than fabricated data. **Two separate, deliberately-independent edit surfaces write to the same `StoredUser.providerProfile` object** — each preserves the other's fields on save rather than clobbering them: Hesap Ayarları > Firma Profili (`provider-profile-editor.tsx`, requires companyName+bio) through `users.ts#updateProviderProfile` (carries `serviceCategories`/`serviceFeatures`/`experienceRange` through unchanged), and Panel > Profilim > Hizmet Bilgilerim (`service-info-editor.tsx`, a completion flow that never requires companyName/bio) through `users.ts#updateProviderServiceInfo` (carries companyName/bio/foundedYear/logoStorageKey/expertise through unchanged). `regions` is the one field both screens genuinely share and either can overwrite. The logo blob lives in the same IndexedDB store as job photos (`photo-blob-store.ts`) under a separate key namespace, uploaded client-side only (not via `/api/job-photos/process`, which stays `hizmet-alan`-gated). Viewed read-only by the counterparty inline within `IncomingOfferCard` (no separate drawer/modal component) — it never reads phone/email/address/tax/TC fields; contact reveal remains solely `contact-access.ts#getRevealedContactForOffer`'s job. `getProviderProfileSummary` computes average rating, in-progress count, and acceptance rate purely from existing `ratings.ts`/`job-requests.ts` data — no separate event log, and no "average response time" metric (dropped: providers initiate offers here, so there's no "provider responded" event to time).
- **Provider identity is anonymized on Gelen Teklifler until an offer is accepted**: `job-requests.ts#isOfferProviderIdentityRevealed(offer)` mirrors `contact-access.ts`'s `ENGAGED_OFFER_STATUSES` timing exactly (identity and phone/email always reveal/hide together, via two deliberately separate "parallel gate" functions rather than one shared one — same pattern as `canViewJobAddress`), and returns `false` for `pending`/`rejected`/`agreement_failed`/`cancelled` — once an offer leaves those states it never re-anonymizes. While hidden, `incoming-offer-card.tsx#getAnonymousProviderLabel(providerId)` shows a deterministic `"Hizmet Veren #NNNN"` label (a non-cryptographic hash of `providerId`, stable across renders/sessions so a requester can still recognize "the same provider" across multiple offers) instead of company name/logo/rating/review count/completed jobs/expertise/bio/region, keeping pre-acceptance evaluation price/duration/description-driven.
- **Service catalog** (`service-catalog.ts`): the platform's single centralized, hierarchical service taxonomy (`SERVICE_CATEGORY_GROUPS`) — feeds *both* a provider's multi-select "Hizmet Bilgilerim" service selection *and* the job-posting/editing "Hizmet Kategorisi" single select (`job-request-form.tsx`, `job-edit-form.tsx`), sharing the same `id` space so a provider's selected service and a job's category can in principle line up (no automatic matching yet — just a shared data foundation). Supersedes but does not remove `jobs.ts#SERVICE_CATEGORIES` (an old flat 8-item list still written by some legacy records); the two are bridged by a one-way, best-effort migration layer — `resolveLegacyJobCategoryToId` (single value, for `Job.category`), `migrateLegacyExpertiseToServiceCategoryIds` (multi-value, for `ProviderProfile.expertise`), and `getCategoryDisplayLabel` (safe display for either old or new values). `"Depolama"` is deliberately left unmapped (no 1:1 equivalent in the new catalog) — migration functions silently skip values they can't map rather than inventing one; original legacy data is never mutated or lost. Also houses `SERVICE_FEATURE_OPTIONS`/`EXPERIENCE_RANGE_OPTIONS` (Aşama 2 additions to `ProviderProfile`) and `getProviderServiceInfoCompletion` (the "Profil Tamamlanma %" checklist shown in `service-info-editor.tsx`).
- **`services-section.tsx`** (the landing page's "Lojistik operasyon hizmetleri" section) renders the same catalog-driven cards to every role but makes them interactive only for a logged-in `hizmet-veren` (`useSession().role === "hizmet-veren"`): `hizmet-alan`/guest get a plain, non-clickable `<div>` card (no "İncele" affordance), while a provider gets a `<Link href="/ilanlar?kategori={category.id}">` card — `provider-job-listing.tsx` reads that `kategori` search param on mount to seed the "Hizmet Türü" filter, so clicking a service card from the landing page lands a provider directly on their "Aktif İlanlar" list pre-filtered to that category. Icons are assigned per `service-catalog.ts` group id (`GROUP_ICONS`, falling back to a generic icon for an unmapped group) rather than per individual category, so adding a new category to an existing group needs no icon change.

### Provider document verification ("Hizmet Veren Belge Kontrolü") & the `admin` role

`hizmet-veren` registration is a KYC-lite gate: a provider must pick 1+ service categories and upload 1+ "Faaliyet Belgesi/Raporu" (activity document/report) before an account exists, and an `admin` later approves/rejects/requests-revision on those documents from a dedicated `/admin` panel. Five modules only make sense together:

- **`provider-services.ts`** is the single source of truth for a provider's current service-category selection — a `{userId, serviceCategoryId}` relational table, following the exact `job-store.ts` module-cache-plus-`useSyncExternalStore` pattern (`providerServicesStore`, subscribed to by `use-provider-services.ts#useProviderServiceCategoryIds` for reactive callers, e.g. the Nakliye isolation hooks below) so a change in one tab (or Hesap Ayarları/Hizmet Bilgilerim in the same tab) is picked up live elsewhere. `setProviderServiceCategoryIds` is a full replace (delete-then-insert, one write), silently drops ids `service-catalog.ts#isServiceCategoryId` doesn't recognize, and is the one write path shared by both the registration form and Panel > Profilim > Hizmet Bilgilerim (`service-info-editor.tsx`). This supersedes the deprecated `ProviderProfile.serviceCategories`/`expertise` fields (see "Provider profiles" above).
- **`provider-documents.ts` + `provider-document-reviews.ts`** split "current state" from "history," the same relationship `Offer.status` has with `notifications.ts`: `StoredProviderDocument` (metadata only — filename/mime/size/`indexedDbStorageKey` into the same `photo-blob-store.ts` IndexedDB used by job/logo photos — plus a **denormalized** `reviewStatus`/`reviewNote`/`reviewedAt`/`reviewedByAdminId`) is the queryable "what's it at now," while `StoredProviderDocumentReview` is an append-only action log ("which admin decided what, when"). The only write path that touches either is `provider-document-reviews.ts#recordProviderDocumentReview(session, input)` — it re-checks `session.role === "admin"` itself (data-layer authority, same pattern as `offers.ts#updateOfferStatus`, not just a UI gate), requires a non-empty note for `rejected`/`revision_requested` (optional for `approved`), and only appends the log row after the denormalized fields actually wrote successfully.
- **`document-validation.ts` + `app/api/provider-documents/validate/route.ts`** mirror the photo-upload pipeline's two-layer pattern exactly (client pre-check / server real validation), extended for document formats: PDF/DOC(X)/XLS(X)/ODT/JPG/PNG/WEBP/HEIC/HEIF/TIF, magic-number-vs-extension cross-checking (`EXTENSION_CONTAINER`), and `hasDangerousDoubleExtension` to catch a script hidden as a middle extension segment (`"rapor.exe.pdf"`). Because `doc`/`xls` share the same OLE-CFB signature and `docx`/`xlsx`/`odt` share the same ZIP signature, the client layer can only classify by container family — the server route (Node-only, `runtime = "nodejs"`) does the deeper check: raw byte-search for known ZIP entry names (`word/document.xml`, `xl/workbook.xml`, `mimetype`/`opendocument.text`) to disambiguate the Office/ODF subtype, and rejects any ZIP containing a `vbaProject.bin` entry (a macro-enabled file renamed to a "safe" extension) regardless of declared extension. Images are further verified by actually decoding them with `sharp` (HEIC/HEIF falling back to `heic-convert`, same as the photo pipeline). This route has no `role`/session check — at the point registration calls it, no real user/session exists yet, so it's input validation only, not an authorization boundary (documented in the route's own comment).
- **`provider-document-consents.ts`** records acceptance of a single, versioned "Belge Doğruruluk Beyanı" (documents-are-genuine declaration) sentence — same versioning principle as `legal-consent.ts` (`recordProviderDocumentConsent` always stamps the *current* `PROVIDER_DOCUMENT_DECLARATION_VERSION`, never a caller-supplied one), but deliberately not a full `LegalDocumentMeta`: it's one sentence shown inline in the registration form, not a multi-section document with its own route/page.
- **`provider-registration.ts#registerProviderAccount`** is the one function `login-form.tsx` calls for `hizmet-veren` signups (the `hizmet-alan` path is untouched and still calls `users.ts#registerUser` directly) — it drives `users.ts#registerUser` + `provider-services.ts` + `provider-documents.ts` + `provider-document-consents.ts` as one manually-simulated "all or nothing" transaction, the same rollback-after-partial-write shape `job-store.ts#createJobsForOperation` uses for photos, just spread across four tables instead of one: documents are uploaded to IndexedDB *before* this function is ever called (so the user can preview/delete them while still filling out the form — `provider-document-upload.tsx`, which deletes any orphaned blob on unmount if the form is abandoned before submit), so every failure path here — including `registerUser` itself failing — deletes those same blobs (`deletePhotoBlobs`), and every failure *after* `registerUser` succeeded also deletes the just-created user plus any of the other three tables' rows already written, via `deleteUserById`/`deleteProviderServicesForUser`/`deleteProviderDocumentsForUser`/`deleteProviderDocumentConsentForUser`.
- **Nakliye-only discovery isolation** (`job-visibility.ts`) is a narrower, deliberately separate rule layered on top of the service-selection data above: a `hizmet-veren` whose `provider-services.ts` selection includes the Nakliye category (`NAKLIYE_SERVICE_CATEGORY_ID`) can only ever *see* Nakliye-category jobs — even if they've also selected other services — while a provider without Nakliye selected is completely unaffected (today's behavior, unchanged). This is a task requirement scoped to Nakliye only; none of the other six service categories get this treatment. The module exports both a flat pair (`isJobVisibleToSession`/`filterVisibleJobs`, fresh `localStorage` read on every call, for one-off checks like `offers.ts#createOffer`) and a reactive pair (`useIsJobVisibleToSession`/`useFilterVisibleJobs`, built on `useProviderServiceCategoryIds`, for components that need to re-render live when a provider's service selection changes — `provider-job-listing.tsx`, `job-detail-content.tsx`, `operation-status-card.tsx`) sharing one pure `resolveVisibility` decision function so the rule is never written twice. It must be applied at the earliest possible read point (right after `useAllJobs()`) so every downstream computation (operation-grouping totals, offer counts, filter results) is automatically correct without further changes — see the module's own doc comment for why. Its own doc comment is explicit that this is a UI-surface guarantee, not a server-side authorization boundary: there's no real backend session (see "No real backend" above), so a technically-capable user could bypass it via devtools; what's guaranteed is that the app's *normal* surfaces (links, notifications, offer forms, offer history) never leak a hidden job through them. Concretely, a provider's *own old offer* on a job that visibility rules now hide (e.g. they added Nakliye after already offering elsewhere) is never silently dropped from `my-offers-panel.tsx` — the offer itself still renders, but the job lookup is guarded so it falls back to a plain "İlan artık mevcut değil" string instead of resolving the real title/category/location (same shape as the unrelated "job actually deleted" fallback elsewhere); `panel-summary.ts`'s Hizmet Veren counters ("Uygun İlanlar"/"Son Hareketler") are likewise computed only over the visibility-filtered job set, never the raw one, so they can't indirectly reveal a hidden job's count or title either.
- **`app/admin`** (`AdminProviderDocumentReviewPanel`, `admin-provider-document-review-panel.tsx`) is the only consumer of this whole feature's read side — gated on `session?.role === "admin"` (an `AuthGateNotice` otherwise), it lists every `hizmet-veren` with at least one uploaded document, grouped by provider (most-recently-uploaded first), showing their selected services, declaration-acceptance state, and a `DocumentRow` per document with Görüntüle/İndir (view/download straight from the IndexedDB blob), Onayla/Reddet/Yeniden Belge İste actions. It reads `getAllProviderDocuments()`/`getAllUsers()` directly rather than through a `useSyncExternalStore` hook (deliberately — this screen is the only consumer, so building shared reactive infrastructure at the `jobs.ts`/`offers.ts` scale would be premature) and just bumps a local `refreshKey` after a successful review action to re-read.

### Çoklu Hizmet Operasyonu (multi-service job creation)

`job-request-form.tsx` (the Hizmet Alan job-creation form, `/hizmet-talebi-olustur`) lets one submission produce **more than one independent `Job`** — e.g. a requester needing both Lashing and a separate Depolama service for the same operation, each with its own dates, gets two fully independent `Job` records rather than one job that awkwardly represents two services. This was built incrementally and the pieces only make sense together:

- **Data model**: `Job.operationId?: string` (a `crypto.randomUUID()`, produced by `job-store.ts#createOperationId`) is the *only* thing that links sibling jobs — there is no separate "operation" table/record. It is purely an internal join key, never a human-facing code (no `MSOP-...`-style display string exists anywhere). `job-store.ts#getJobsByOperationId(operationId)` / `getSiblingJobs(jobId)` (the latter: resolve the job, return `[]` if it has no `operationId`, else return `getJobsByOperationId` minus itself) are the only two query helpers — both operate purely over `readUserCreatedJobsSnapshot()` (user-created jobs only; the static `jobs.ts` seed listings can never have an `operationId`).
- **Two independent creation paths, deliberately not unified**: `job-store.ts#createJob` (single job, unchanged from before this feature — no `operationId` is ever written by it) and `job-store.ts#createJobsForOperation` (`services: OperationServiceInput[]`, **rejects** anything with fewer than 2 entries with an explicit error rather than silently delegating to `createJob`). Deciding which to call is the *form's* job (`job-request-form.tsx`'s `services.length === 1` branch), not the data layer's — `createJobsForOperation` refuses to be a drop-in replacement for the single-job path.
- **Every field is per-service, not operation-wide** — category, title, description, dates (`workDate`/`workEndDate`), and the full location (district/facility/address/custom-mode fields) all live on each `OperationServiceInput` entry. Only `province` (always "Kocaeli"), `operationDetails`, and the photo set are genuinely shared across the whole operation. In the form, each service is a `ServiceEntry` (local React state, `job-request-form.tsx`) keyed by a client-only `localId: crypto.randomUUID()` — never sent to the data layer, never used as an array index for identity (so deleting a middle card can't corrupt a later card's state, and React never confuses two cards after a reorder).
- **"Ana hizmetle aynı lokasyon"**: every service after the first (`index > 0`) has a `useMainLocation` toggle, checked by default. When checked, `job-request-form.tsx#getEffectiveLocation` resolves that service's location fields from the *first* service (`services[0]`) instead of its own (empty) ones — this is a form-only convenience; `createJobsForOperation` itself has no concept of "same as main," it just receives each service's already-resolved location. Unchecking reveals that card's own full İl→İlçe→Bölge/Tesis→Açık Adres picker (same `SearchableSelect` flow as "Centralized job location" below).
- **Atomicity without a real transaction**: `createJobsForOperation` validates everything up front (category count/uniqueness/catalog-validity via `service-catalog.ts#isServiceCategoryId`, each service's own date-range sanity — deliberately re-checked here even though `createJob` never validates `workDate` itself, since multiple independent ranges arriving in one call warrant the extra defense — and photo count), then persists a **separate** copy of the shared photos for *each* service (`persistPhotosOrRollback` called once per service, fresh `storageKey`s every time) before writing anything to the jobs table. If any one service's photo persistence fails, every already-persisted sibling's blobs are deleted and the function returns an error *before* `writeUserCreatedJobs` is ever called — so a failure never leaves a partial operation (some jobs created, some not). The one deliberate cost of per-service photo copies (rather than a shared `storageKey`) is that the same image is duplicated in IndexedDB once per sibling service — necessary because `deleteJob`/`deleteJobPhoto` delete blobs by `storageKey`, and siblings must be deletable independently without corrupting each other's photos (see "sibling jobs are fully independent" below).
- **Sibling jobs are fully independent after creation** — same `operationId`, otherwise no relationship is enforced anywhere. There is no "the whole operation closes if one job closes" logic, no bulk edit/cancel/offer/notification of any kind. Offers, capacity, contact reveal, completion, disputes, ratings — every mechanism described elsewhere in this document keys off a single `Job`/`Offer`, and none of them were touched to special-case multi-service operations; a sibling job is, to every other system in the app, just another ordinary job that happens to share a `Job.operationId` value. The UI *does* surface the relationship for discovery/status purposes (see "Operation discovery & status UI" below) but never for bulk action — each sibling still takes its own independent offer/accept/complete/rate path through the existing single-`Job` machinery.
- **Operasyon Önizleme (preview) is a client-side mode switch, not a route.** `job-request-form.tsx` holds a `mode: "form" | "preview"` state on the *same* component — submitting the form (`handleSubmit`) only validates (shared `operationDetails`/photo count via `job-form-validation.ts#validateSharedOperationFields`, each service via `validateServiceItem`, cross-service duplicate categories via `findDuplicateServiceCategoryIds`) and flips `mode`, it never calls `createJob`/`createJobsForOperation` itself. The preview renders every service's *resolved* data (real district/facility name, never a literal "same as main" placeholder) plus a single shared-photo thumbnail (`URL.createObjectURL` on `photos[0].blob`, revoked on change/unmount — photos are never re-uploaded for the preview). Its own "İlanı Yayınla" / "N Hizmet İlanını Yayınla" button (`handlePublish`) is the **only** place either creation function is actually invoked; "← Düzenlemeye Dön" just flips `mode` back — since nothing unmounts, no form state is ever lost. The same synchronous `submitLockRef` double-submit guard used elsewhere in this form now guards `handlePublish` instead of the form's `onSubmit`.
- **Post-creation redirect**: single service still goes to `/ilanlar/${job.id}` (unchanged). Multiple services redirect to `/panel/hizmet-taleplerim?operasyonIlanSayisi=${count}` — no new operation-detail route/page exists (deliberately out of scope) — and `job-requests-panel.tsx` reads that query param to show a "`{count}` hizmet ilanı başarıyla oluşturuldu." banner, following the exact same static (non-auto-dismissing) query-param-banner pattern already used there for `guncellendi=1` (set by `job-edit-form.tsx` after a single-job edit).

#### Operation discovery & status UI

A single card on `job-detail-content.tsx` (`/ilanlar/[id]`, not gated by role) and one grouping layer on the provider job listing surface an operation's siblings **purely for discovery/status** — it does not create a bulk-action surface; every "Teklif Ver"/accept/complete path still lands on a single `Job`/`Offer` exactly as described above.

- **`operation-status-card.tsx` ("Operasyon Durumu") is the only place on the page that lists an operation's sibling services** — it went through two prior, wrong iterations before landing here, worth knowing both so the history doesn't repeat: (1) it once coexisted with two sibling cards, `operation-sibling-jobs-card.tsx` ("Bu Operasyondaki Diğer Hizmetler") and `operation-service-offers-card.tsx` ("Operasyondaki Hizmetler", the one with the "Teklif Ver" link), all three rendering the *same* sibling list independently; (2) an attempt to "simplify" that only consolidated each row's *text* (folding a global badge + a viewer-specific note into one label) while still leaving all three cards standing — still three separate sections showing the same data. Both are gone: the two sibling files were deleted outright and every case they covered (data, status derivation, the "Teklif Ver" action, the sibling-row `Link` navigation) was folded into this one card's own row list, below its existing progress bar/summary tiles (which this consolidation did not change). Reads the full sibling list via `use-jobs.ts#useJobsForOperation(operationId)` (wraps `job-store.ts#getJobsByOperationId`, so ordering is always true creation order, never the reversed/newest-first order `useAllJobs()` uses elsewhere).
- **Status bucketing is centralized** in `job-requests.ts`: `getOperationStatusBucket(job, offers)` derives one of `OperationStatusBucket` (`getJobRequestFilter`'s 4 values + an `"iptal"` fallback) per job, `getOperationStatusBucketLabel`/`Tone` render it (now only for the card's own aggregate summary tiles — see below), and `accumulateOperationStatusCounts(jobs, getBucket)` is the shared reduce-to-summary helper behind `getOperationStatusSummary` (real, job-level truth — what the listing-page grouping below uses) and `getPublicOperationStatusSummary` (`getBucket` is injected precisely so summaries can share the counting math without duplicating it) — `operation-status-card.tsx`'s progress bar/summary tiles (Toplam Hizmet/Teklife Açık/Devam Ediyor/Tamamlandı/İptal Edildi) use the latter, GLOBAL/job-geneli and identical for every viewer; this aggregate layer is unrelated to the per-row status below and was not touched by the row-consolidation work.
- **Each sibling row shows exactly one status/action, from one function** — `offers.ts#getOperationServiceCardStatus(job, offers, session, {allowOfferAction})` — no parallel "global badge + personal note" pair (that was exactly the earlier, wrong design). It either returns `{kind: "teklif-ver"}` (this viewer, a `hizmet-veren`, can genuinely submit a new offer here — same gate as `canProviderSubmitNewOffer`/`offer-panel.tsx`) or `{kind: "label", label, tone}`, a single already-resolved string ("Teklif Bekliyor", "Teklif Kabul Edildi", "Devam Ediyor", "Tamamlama Onayı Bekleniyor", "İtiraz Sürecinde", "Tamamlandı", "İptal Edildi", "Başka Hizmet Verenle Anlaşıldı", "İşe Başlama Onayı Bekleniyor", or the generic "Teklife Açık" fallback) — resolution order and viewer isolation (own offer via `getOfferForJob` checked before any job-level fallback; a sibling's offer never leaks into another viewer's row) are documented on the function itself, not duplicated here. `allowOfferAction: !isCurrent` — the row for the job currently being viewed never shows "Teklif Ver" (its own real offer form is already on the same page, in the `OfferPanel` above) and is marked "(Bu ilan)" instead; that row is also the only one that isn't a link. Every other (sibling) row is a `<Link href="/ilanlar/[id]">` wrapping the whole row (preserving the old sibling-card's click-to-navigate/discovery behavior) — "Teklif Ver" renders as a plain `<span>` styled like a button *inside* that link rather than a nested `<a>`, since clicking anywhere on the row already goes to that job's own page where the real `OfferPanel` lives.
- **Aktif İlanlar listing grouping** (`job-listing-row.ts#groupJobListingRowsByOperation`): collapses 2+ sibling rows already surviving the filter bar into one `OperationListingItem` (`job-listing-table.tsx`/`job-listing-cards.tsx` render it in the *same* columns/card shape as a normal row — a dynamic "Hizmet Türü" badge replaces the category chip, a progress line reuses the closedReason note's slot — no new columns, ordinary single-job rows are pixel-identical to before). The representative/"primary" row is the true first-created sibling (via `getJobsByOperationId`, independent of the list's own display order) among currently-visible survivors. **The filter only ever decides whether an operation appears at all** (any one sibling passing the filter is enough) **— it never shrinks what the card reports**: total/completed/progress/summed-offer-count always come from the operation's full sibling set (`getOperationStatusSummary`, the real/job-level version — this listing is provider-only, so there's no owner-vs-viewer ambiguity to begin with), not just the filtered-visible subset. Getting this backwards was an actual shipped bug (Aşama 5.1): a filter that matched only 1 of an operation's 3 services used to make the whole operation look like a plain single-service job with a truncated total.
- **The badge and its detail line track per-service completion, not just total/progress.** `job-listing-row.ts#getJobListingCategoryBadgeLabel` (shared by table/cards, `job.title`/"İlan Başlığı" is never touched by it) renders `"{kategori} Hizmeti Arıyor"` for a single job, or `"Operasyon • {kalan} Hizmet Arıyor"` for an operation where `kalan = totalCount - completedCount` (both from `getOperationStatusSummary`, never guessed from progress percent) — a completed service drops out of `kalan` but the badge is never shown reading "0 Hizmet Arıyor" because the whole row disappears first (next bullet). Directly below the badge, `operation-service-tags.tsx#OperationServiceTags` (same shared-component pattern) lists **every** service in an operation (service-catalog order, never truncated/collapsed behind a "+N") as inline `·`-separated text, styling a completed one (`OperationServiceSummary.isCompleted`, from `getOperationStatusBucket`) with muted/strikethrough text rather than a removed/replaced tag — so a still-open sibling and a finished one are visible side by side.
- **Completed jobs/operations are removed from "Aktif İlanlar" entirely, a fourth gate alongside expiry/closure.** `job-completion.ts#isJobFullyCompletedForListing(job, offers)` is the single source of truth `provider-job-listing.tsx`'s `activeJobs` filter checks (`!isJobListingExpired && !isJobManuallyClosed && !isJobFullyCompletedForListing`): a single job counts once its own `getOperationStatusBucket` is `"tamamlandi"`; an operation counts only once **every** sibling (via `getJobsByOperationId`, the full set, not just filter-visible ones) is `"tamamlandi"` — one still-open sibling keeps the whole operation visible. Same non-deleting architecture as the publish-window/closure gates: `Job.status` is never touched, nothing is deleted, the job/operation just stops appearing in this one discovery surface — `my-offers-panel.tsx`/`job-requests-panel.tsx`'s "Tamamlandı" tabs, `panel-summary.ts` counters, and `operation-status-card.tsx` (which must keep showing a completed operation's full history) all derive their own status independently and never call this function.

### İlan Yayın Süresi Yönetimi (job listing publish window)

`app/_lib/job-publish-window.ts` is the single source of truth for how long a `Job` stays active: every listing publishes for exactly `JOB_PUBLISH_WINDOW_DAYS` (14) days from `Job.createdAt`. Expiry never deletes the job — it only drops out of active lists/search/offer capacity and becomes manageable from a dedicated "Süresi Dolan İlanlar" tab (below). Every function in the file is pure and takes an optional `now: Date = new Date()` parameter, with no timer/scheduler anywhere — the state is recomputed on every read, by design, so the same logic could move server-side (a cron/queue worker) later with zero changes (see the file's own closing comment).

- **Window math**: `computePublishEndAt(startIso)` adds `JOB_PUBLISH_WINDOW_DAYS` in raw milliseconds (`Date.getTime()`), never calendar-day arithmetic — this deliberately avoids DST/timezone shifting a listing's close time by an hour depending on when/where it's viewed. `getJobPublishEndAt(job)` prefers the stored `publishEndAt`, falling back to deriving it from `createdAt` if missing. `createPublishWindow(now)` produces the `{createdAt, publishEndAt}` pair and is called **only** from `job-store.ts#createJob`/`createJobsForOperation`/`republishJob` — no other call site should hand-compute either field.
- **Legacy-safe default**: a job with no reliable `createdAt` (pre-dates this feature) is never treated as expired — `isJobPublishWindowExpired` returns `false` whenever `getJobPublishEndAt` can't resolve a date, rather than guessing.
- **Critical exception, shared with the offer-workflow rules**: `isJobListingExpired(job, offers, now)` is date-expiry AND-ed with `job-requests.ts#getSettledOfferForJob(job.id, offers) === null` — a job whose offer has reached `accepted`/`in_progress`/`completion_requested`/`completion_disputed`/`completed` is **never** counted as expired regardless of the date, using the exact same status set the rest of the app already treats as "settled" (no new threshold invented). If that offer later falls out of the set (`agreement_failed`/`cancelled`), the job becomes subject to the publish-window rule again — same reversal pattern as re-offering eligibility elsewhere in this doc. `isJobListingActiveForOffers` is just the negated, named form of this same check, used for readability at offer-gating call sites. `isExpiredListingAwaitingAction(job, offers, now)` is a narrower, separate check — expired **and** not yet `republishedToJobId` — used wherever a *second*, already-handled expiry shouldn't re-surface (notification, panel counter; see below), as opposed to the "Süresi Dolan İlanlar" tab itself, which still lists every expired job (republished or not) so history stays visible.
- **Where it's enforced**: `offers.ts#canProviderSubmitNewOffer` and `#createOffer` both check `isJobListingExpired` as an independent, later gate than `isJobClosedToNewOffers` — an expired listing can't collect brand-new offers even before that other check would fire. `getOperationServiceCardStatus` deliberately shows the more specific "İşe Başlama Onayı Bekleniyor" instead of "Süresi Doldu" when a pending offer is still awaiting the requester's decision on an already-expired listing (see job-publish-window.ts's own note on why this doesn't conflict with the settled-offer exception above). `provider-job-listing.tsx`'s "Aktif İlanlar" filters out expired jobs entirely (`job.status === "yayinda" && !isJobListingExpired(job, offers)`) — the seeded example listings (no `createdAt`) never need special-casing since they simply never expire.
- **Republishing** (`job-store.ts#republishJob`) is the sole authorized entry point for "Yeniden Yayınla." It clones rather than mutates: the old `Job` is left untouched except for a new `republishedToJobId`, and a brand-new `Job` (new id, fresh `createdAt`/`publishEndAt` — a new 14-day window, user-supplied `workDate`/`workEndDate`, freshly-copied photo `storageKey`s via `duplicateJobPhotos` — same independent-copy rationale as multi-service operation photos) is created with every other field copied verbatim. The two-way link (new `republishedFromJobId` = old id, old `republishedToJobId` = new id) makes history traceable in both directions. A second republish attempt against the same already-republished old job is rejected outright (`existing.republishedToJobId` already set) — a listing can never fan out into more than one active successor. Offers stay keyed to `jobId`, so the republished job structurally starts with zero offers — no filtering code needed to keep the old listing's offers from leaking in.
- **"Süresi Dolan İlanlar" tab** (`job-requests-panel.tsx`, between "Aktif" and "Devam Eden") renders a dedicated card per expired job (createdAt/publishEndAt, a "Süresi Doldu" status, and Yeniden Yayınla/Kalıcı Olarak Sil actions) — "Kalıcı Olarak Sil" reuses the exact same `DeleteJobDialog`/`offers.ts#deleteJobWithOffers` path as ordinary deletion elsewhere in the panel, not a separate delete flow. Once a listing has been republished, its card drops the action buttons in favor of a link to the new listing, matching the data-layer's own already-republished guard.
- **Surfacing**: `panel-summary.ts#expiredListingCount` counts `isExpiredListingAwaitingAction` jobs — mutually exclusive with `activeRequestCount`, which now also excludes expired jobs, so a real job lands in exactly one bucket. `notifications.ts`'s `ilan_yayin_suresi_doldu` ("İlan Süresi Doldu") is the **one** `NotificationType` derived directly from a `Job` rather than an `Offer` (no `offerId`) — built straight from `isExpiredListingAwaitingAction` over the requester's own jobs, `id: listing-expired-${job.id}`, `createdAt` set to `publishEndAt` (the real event time). It persists until the job is republished, at which point `republishedToJobId` being set removes it — consistent with the rest of "Notifications are derived, not stored" below.

### İlan Kapatma (manual job closure)

`app/_lib/job-closure.ts` is a second, independent way a `Job` stops being active — deliberately the same architecture as the publish-window feature above (job never deleted, `Job.status` never touched, state derived from a stamped field, no `Offer`-status invented) but triggered by the requester's own decision rather than a date. `Job.closedAt`/`Job.closureReason` (`JobClosureReason`: `baska-hizmet-verenle-anlasildi` | `hizmete-ihtiyac-kalmadi` | `yanlislikla-olusturuldu` | `diger`) is the one field pair `isJobManuallyClosed(job)` checks — the single source of truth, read by `job-requests-panel.tsx`, `notifications.ts`, and `offers.ts#getOperationServiceCardStatus` (checked *before* any offer-derived branch there, since closing also flips still-`pending` siblings to `rejected` and would otherwise mislabel as "Başka Hizmet Verenle Anlaşıldı").

- `offers.ts#closeJobListing(session, jobId, reason)` is the sole write path — requester-owner only, rejects if already closed (`JOB_ALREADY_CLOSED_MESSAGE`) or if `job-requests.ts#isJobClosedToNewOffers` is already true (`JOB_CLOSURE_BLOCKED_MESSAGE`) — i.e. closing is only possible before any offer starts real work, the same `accepted`-but-not-yet-`in_progress` threshold used everywhere else in this doc. Any still-`pending` sibling offers are then flipped to `rejected`, best-effort (logged, not surfaced, on failure — same pattern as `deleteJobWithOffers`'s sibling-offer write).
- Rejected provider(s) get a notification whose message varies by reason (`job-closure.ts#getJobClosureNotificationMessage`) — `notifications.ts` distinguishes this from an ordinary `teklif_reddedildi`/`hizmet_kalemi_kaldirildi` by checking `job.closedAt` (a third branch alongside "job still exists" vs. "job was deleted," see "Notifications are derived, not stored" below).
- `job-requests-panel.tsx` gets a dedicated "Kapatılan İlanlar" tab (mutually exclusive with "Süresi Dolan İlanlar" — `isJobManuallyClosed` is checked first, so a closed-*and*-expired job always shows as closed) with its own "İlanı Kapat" confirmation dialog (reason picker, same modal shell as `DeleteJobDialog`) — a real, distinct terminal state, not a substitute for deletion, and independent of/checked earlier than `offers.ts#deleteJobWithOffers`.

### Provider job listing ("Aktif İlanlar")

The Hizmet Veren's `/ilanlar` screen is `provider-job-listing.tsx` (swapped in by `job-listing-screen.tsx` when `session.role === "hizmet-veren"`; the guest and Hizmet Alan branches render the separate, unchanged `JobList`/`JobCard`). It's a single unified "Aktif İlanlar" list, not split into "Teklife Açık"/"Teklife Kapalı" sections — `getJobAvailabilityForProvider`'s per-row `open`/`closedReason` (see "New offers vs. accepted vs. work started" above) still surfaces as a small note under "İlanı İncele" (`getProviderClosedReasonLabel`, e.g. "İş Devam Ediyor" once a job's settled offer passes `accepted`), it just never gates which section a row appears in. There is also no favorites feature and no listing-badge system (Yeni/Acil/Teklif Bekliyor/etc.) — both were removed after shipping; `StatusBadge` itself is untouched and still used by other screens (offer/job status chips), only this screen's own badge computation (`job-listing-badges.ts`) was deleted. There is also no page heading, description paragraph, or "Son Görüntülenenler" strip anymore (removed 2026-07-26) — the compact filter toolbar is the first thing rendered, deliberately so the job list itself (not the filter chrome) is what a Hizmet Veren sees first; `recently-viewed-jobs.ts`/`use-recently-viewed-jobs.ts` still exist and `recordJobViewed` is still called from `handleJobClick` (so click history keeps accumulating), but nothing currently reads it back — an intentional "keep tracking, drop the display" choice in case the strip returns later. The feature is layered so the same per-job computation feeds both responsive render paths:

- `job-listing-row.ts#buildJobListingRows(jobs, offers, providerId)` is the single row-data builder (thumbnail photo, visible offer count, `getJobAvailabilityForProvider` availability, `job-location.ts#getJobLocationSummary` location) — computed once per job, consumed identically by `job-listing-table.tsx` (desktop, a real `<table>`, 7 columns: Fotoğraf/Hizmet Türü/İlan Başlığı/Firma-Bölge-Konum/İş Tarihi/Teklif Sayısı/İşlem) and `job-listing-cards.tsx` (mobile card list). Neither ever renders `Job.addressText` — see "Centralized job location" below for why.
- **Only one of the two trees is ever mounted**, chosen via `use-media-query.ts#useMediaQuery("(min-width: 1024px)")` rather than rendering both and toggling visibility with CSS — that CSS-both-trees approach was tried first and reverted after it broke an existing regression test (duplicate `<a>` elements sharing the same job title, a Playwright strict-mode violation) and silently doubled `useJobPhotoUrl`/IndexedDB work per row. A `matchMedia`-driven client read is safe here specifically because this whole subtree only ever mounts after `useSession()` resolves to a real session (`getServerSnapshot` is always `null`), so there is no SSR-hydrated markup for it to mismatch against.
- **The filter toolbar is deliberately thin and backgrounded, not the page's focal point** (`job-listing-filter-bar.tsx`) — there is no search box at all anymore (removed 2026-07-26, along with `job-listing-search-bar.tsx` and `job-listing-filters.ts#matchesJobSearch`, both deleted rather than left unused): six equal-width fields (Hizmet Türü, İl, İlçe, Bölge/Tesis, Tarih, Teklif Durumu) in one `grid-cols-1 sm:grid-cols-3 lg:grid-cols-6` grid — mobile stacks one per row, tablet wraps into two tidy rows of three, desktop is a single row. Tarih/Teklif Durumu are `SearchableSelect`s too (not the old pill-style `SegmentedControl`, removed) purely so every field shares the same height/padding as the others — their options (`DATE_BUCKET_OPTIONS`/`OFFER_STATUS_FILTER_OPTIONS`) already include their own "Tümü" entry, so unlike Hizmet Türü/İlçe/Bölge-Tesis they are *not* prefixed with the synthetic `CLEAR_OPTION`. Every `SearchableSelect` here passes `compact` (a new opt-in prop, default `false`) for tighter padding/smaller icon/quieter label — job-request-form.tsx/job-edit-form.tsx/login-form.tsx don't pass it, so their `SearchableSelect`s look exactly as before. The toolbar card itself uses a smaller `rounded-[10px]` (not the app-wide `rounded-card`, which is a much softer 0.875rem used for actual content cards) plus `shadow-sm`, matching the "recede into the background" intent. `job-listing-screen.tsx`'s hizmet-veren branch uses `pt-4` (not the site-wide `py-16` page-padding convention every other section keeps) so the toolbar sits right under the sticky header.
- **`SearchableSelect`'s dropdown popup can now open wider than its trigger** (`searchable-select.tsx`, `min-w-full` + content-fit `w-max` capped at `max-w-[min(320px,90vw)]`, option-label `truncate` removed) — this was a real bug, not scoped to this screen: cramming this toolbar's fields into narrow grid tracks made the popup inherit that narrow width too, so long option labels (e.g. "Konteyner Boşaltım", "Tehlikeli Madde Depolama") got cut off mid-word inside the *open list*. Fixed at the shared-component level since a narrow trigger with a wide popup is a universally-safe pattern (every other `SearchableSelect` caller already has a full-width field, so this is a no-op improvement there). The closed trigger's own selected-value text still truncates by design — that's a deliberate, compact-toolbar trade-off, not the bug that was reported.
- **Filters are deliberately grounded in the same central catalogs the job-creation form uses (`service-catalog.ts`, `turkey-locations.ts`), not in ad-hoc string comparisons on live job data** — `job-listing-filters.ts` is the single source of truth for both option-building and row-matching, so the two can never drift apart:
  - **Hizmet Türü**: options come from the *entire* `SERVICE_CATEGORY_GROUPS` catalog (`buildCategoryOptions`, no `jobs` param) — unlike the other filters below, a category with zero current listings still appears, and a removed/legacy category (`jobs.ts#SERVICE_CATEGORIES` raw text) never appears as an option. Matching (`matchesJobCategory`) goes through `resolveLegacyJobCategoryToId(job.category)` so both new (id-based) and legacy (raw Turkish text) jobs resolve to the same catalog id; a legacy value with no mapping (e.g. "Depolama", deliberately unmapped — see `service-catalog.ts`) simply never matches a specific category selection, same known limitation as everywhere else that function is used.
  - **İl**: MALSEVK is Kocaeli-only for now, so İl is **not** a `SearchableSelect` — it's a fixed, readonly field (a `Lock`-iconed box always reading "Kocaeli", `FIXED_PROVINCE_LABEL` in `job-listing-filters.ts`) and `filters.province` always equals `FIXED_PROVINCE_KEY` (`slugifyTurkish("Kocaeli")`), which also actively filters out any non-Kocaeli job (including the seeded `İzmir`/`İstanbul` example listings) via the same `matchesProvinceFilter` used before — this is a real data filter, not just a cosmetic lock. `buildProvinceOptions` (option-builder for a province dropdown) and the general-purpose `matchesProvinceFilter`/`resolveJobProvinceKey` are deliberately left in `job-listing-filters.ts`, unused-by-the-UI but otherwise untouched, so a future nationwide rollout only needs to swap the readonly block back for a `SearchableSelect` fed by `buildProvinceOptions` — no filtering-logic change required (same kept-for-later pattern as `job-requests.ts#getJobOfferAvailability`'s unused `"kapali"` branch).
  - **İlçe**: **not** job-data-scoped (fixed 2026-07-26 — it used to only list districts that already had at least one active job in them, so most of Kocaeli's 12 official districts silently never appeared) — options now come from `turkey-locations.ts#getDistrictsByProvinceCode` (`app/_data/turkey/districts.json`, the same static reference data `getProvinces()`/district pickers elsewhere already read), resolved from the province *slug* via the new `turkey-locations.ts#getProvinceCodeBySlug`. `buildDistrictOptions(selectedProvinceKey)` therefore always lists all 12 Kocaeli districts regardless of live job data, matching how Bölge/Tesis already worked. Row-matching is unchanged — still `matchesDistrictFilter` → `resolveJobDistrictKey`/`getDistrictId`.
  - **Bölge/Tesis**: the one filter that is *not* job-data-scoped — options come straight from `turkey-locations.ts#getFacilitiesByProvinceAndDistrict(provinceKey, districtKey)` (a same-array, no-type-filter sibling of `getFacilitiesByProvinceDistrictAndType`), so it can show a facility (e.g. Beldeport/Yılport Gebze in Kocaeli/Dilovası) even if no job currently references it by name, and conversely a facility whose real verified district differs from what a job's free-text `workLocationType` implies (e.g. "Safiport Derince Limanı" is `districtId: "derince"` and `active: false` in `data/locations/locations.json`, not Dilovası) correctly never shows there. Disabled until a district is selected. Row-matching (`matchesFacilityFilter` → `job-location.ts#resolveJobFacility`) prefers `Job.facilityId` (set when the job-creation form's Bölge/Tesis picker resolved to a real catalog facility) and falls back to a name/alias fold-match on `Job.workLocationType` *within that job's own province+district* for jobs created before `facilityId` existed; jobs whose `workLocationType` is a generic description ("Fabrika", "Kapalı Depo") rather than a specific catalog facility name never match a specific facility filter — a known, accepted limitation, not a bug.
- `recently-viewed-jobs.ts`/`use-recently-viewed-jobs.ts` is a per-user localStorage store following the exact `notification-reads.ts` convention (module cache, `Set<() => void>` listeners, stable `getServerSnapshot`). "Recently viewed" is recorded via the row's own link `onClick` inside the listing screen — deliberately not by instrumenting `job-detail-content.tsx`, which stays untouched.
- Rows belonging to the same `Çoklu Hizmet Operasyonu` operation are collapsed into one row/card here — see "Operation discovery & status UI" under that section above for `groupJobListingRowsByOperation` and the filter-visibility-vs-content distinction.

### Centralized job location

`app/_lib/job-location.ts` is the single module every screen goes through for anything derived from a `Job`'s location fields — no component hand-concatenates `province`/`district`/`workLocationType` itself:

- `toFacilitySelectOptions(facilities)` builds the `SearchableSelect` options for the merged **"Bölge / Tesis"** picker used identically by `job-request-form.tsx` (both the single-service form and each service card of the multi-service flow — see "Çoklu Hizmet Operasyonu" above) and `job-edit-form.tsx` (İl → İlçe → Bölge/Tesis → [custom-facility fields, only in custom mode] → Açık Adres, in that order). There is deliberately no separate "İşin Yapılacağı Yer Türü" step anymore (removed 2026-07-25) — the picker lists every facility type together for the chosen il+ilçe via `turkey-locations.ts#getFacilitiesByProvinceAndDistrict`, the exact same source and il/ilçe keying the Aktif İlanlar Bölge/Tesis filter already used, so the two screens can never drift onto different facility lists again. Each option's facility type shows as a `hint` (e.g. "Beldeport" hinting "Liman"), and a synthetic `FACILITY_FREE_TEXT_VALUE` option — labelled **"Listede yok — tesis bilgilerini kendim gireceğim"** (`CUSTOM_FACILITY_OPTION_LABEL`) — switches the form to custom-facility mode (below) instead of blocking creation when a job's real location isn't in the catalog. A "Hazır listeden seçmek için tıklayın." button lets the user go back to the `SearchableSelect` from custom mode (`handleFacilityChange("")`) — every caller needs this same round-trip, it's not automatic.
- **`companyOrFactoryName` ("Firma / Fabrika Adı") is legacy-only** — removed from both the job-creation and job-edit forms entirely as part of MALSEVK's Kocaeli-only simplification; no current screen collects it. `job-store.ts#resolveLocationFields` deliberately omits it from its return value, and since `updateJob` applies that result as `{...existing, ...resolveLocationFields(input)}`, a pre-existing job's value (if any) survives untouched across later edits even though the field is never shown again — no data loss, just a retired input. `job-location.ts#getJobLocationSummary` still reads `job.companyOrFactoryName` for display, purely for back-compat with jobs created before the field was removed.
- **Custom facility mode** (`Job.locationMode: "custom"`, Hizmet Alan-only, job create/edit only — never reachable by `hizmet-veren` or guests, gated the same way the rest of the form is): picking the free-text option shows a single **"Tesis / İşletme Adı"** field that reuses `workLocationType` itself, plus three new optional fields with no catalog/free-text equivalent: `neighborhood` ("Bölge / Mahalle"), `locationUrl` ("Konum Bağlantısı", validated as `http(s)://...` if non-empty), `directionsNote` ("Adres Tarifi"). `facilityId` is force-cleared to `undefined` in this mode by `job-store.ts#resolveLocationFields` regardless of what the caller passes — a custom entry can never carry a fabricated `Facility.id`. There is intentionally **no pre-built catalog of individual factories/companies** to choose from instead (a `FABRIKA` catalog of ~10 flagship Kocaeli plants was built via `location_manual_overrides.json` and then fully reverted 2026-07-25) — MALSEVK's location catalog is scoped to shared/official location types only (Liman, OSB, Serbest Bölge, Lojistik Merkezi); a single company's own site is always entered ad hoc, never pre-cataloged.
- `resolveJobFacility(job)` resolves a `Job` back to a `Facility` — returns `null` immediately for `locationMode: "custom"` jobs (skips catalog matching entirely, so a custom-typed name can never accidentally resolve to a real facility by coincidental name/alias match), otherwise prefers `job.facilityId` (validated against the job's own province+district) and falls back to a name/alias fold-match on `job.workLocationType` for jobs created before `facilityId` existed. This is the *only* copy of that resolution logic; `job-listing-filters.ts#matchesFacilityFilter` imports it rather than keeping its own.
- `getJobLocationSummary(job)` / `formatJobLocationLine(job)` are what every rendering surface calls instead of inline string-building: `job-card.tsx`, `job-requests-panel.tsx`, `incoming-offer-card.tsx`, `my-offers-panel.tsx`, and `job-listing-row.ts` (table/cards) all use one of these two — none of them needed to change for custom mode, since `facilityDisplayName` already falls back to `workLocationType` verbatim when `resolveJobFacility` returns `null`. `formatJobLocationLine` deliberately omits `companyOrFactoryName` (e.g. `"İMES OSB • Dilovası / Kocaeli"`) — callers that also want the company name (the listing table/cards, the job detail page) read it separately off the summary and render it as its own line.
- **`Job.addressText`/`neighborhood`/`locationUrl`/`directionsNote` are never included in either helper** — all four share one gate, `job-requests.ts#canViewJobAddress(session, job, offers)` (same `ENGAGED_OFFER_STATUSES` timing as `contact-access.ts`'s phone/email reveal, plus an "owner always sees their own" exception). `job-detail-content.tsx` is the only screen that renders them, conditionally, right after Firma/Fabrika Adı → Bölge/Tesis → İlçe/İl; `job-requests-panel.tsx` renders them unconditionally instead of calling the gate, because that panel is already structurally filtered to `job.requesterId === session.id` (the one case the gate always allows anyway). No other screen (listing table/cards, offer cards, job-card.tsx) ever reads them.
- Legacy back-compat: `job-store.ts#normalizeStoredJob` coerces `facilityId`/`companyOrFactoryName`/`addressText`/`locationMode`/`neighborhood`/`locationUrl`/`directionsNote` to `undefined` unless the stored value is actually a string (same pattern already used for `photos`; `locationMode` additionally requires the value to be exactly `"catalog"` or `"custom"`), so pre-existing localStorage jobs and the static `jobs.ts` seed listings (which have none of these fields) render their fallback (`workLocationType` verbatim, no company line, no address line) rather than crashing or showing `"undefined"`. A missing `locationMode` is always treated as catalog mode — editing such a job requires filling in Açık Adres before saving (catalog-mode rules); it no longer also requires Firma/Fabrika Adı now that that field has been removed from the forms entirely (see above).

### Notifications are derived, not stored

`notifications.ts` computes each user's `AppNotification[]` live from the current `Offer.status` (plus `Offer.createdAt`) every render — there is no separate notifications/events table. This is why notification ids stay stable (derived from `offer.id` + event name) and why read/dismissed state (tracked separately, see below) keeps matching up correctly across sessions. One consequence to keep in mind when adding a new offer-status transition: notifications tied to a **transient** status (e.g. `accepted`, `completion_requested`) disappear on their own the moment the offer moves past that status, because the derivation only ever looks at the offer's *current* status; only notifications tied to a **terminal** status (`completed`, `rejected`, `cancelled`, `agreement_failed`, `withdrawn`) persist. Requesters and providers each get their own distinct set of `NotificationType`s derived from the same offers — never the other role's. Almost every notification filters `myOffers` by the viewer's *own* `offer.status`; the one exception is `baska_hizmet_verenle_anlasildi` ("Başka Bir Hizmet Verenle Anlaşıldı"), which instead filters the viewer's still-`pending` offers by whether a *sibling* offer on the same job has closed them (`getProviderOfferFilter(offer, offers) === "kapanan-teklifler"`) and reads that sibling's `updatedAt` for `createdAt` — see "Provider offer tabs" above. Read state (`notification-reads.ts`) and dismissed state (`notification-dismissals.ts`) are two separate per-user localStorage keys (`malsevk_read_notifications_<userId>` / equivalent for dismissals) — intentionally not cleared by `clearSession()`, so logging out and back in doesn't reset what a user has already seen or dismissed.

**Deleting a job doesn't delete its offers.** `offers.ts#deleteJobWithOffers` (the authorized entry point for job deletion — never call `job-store.ts#deleteJob` directly) used to delete every associated `Offer` along with the job; now any still-`pending` offer on that job is instead flipped to `rejected` (an existing status, not a new one) and kept, while already-terminal offers (rejected/withdrawn/agreement_failed/cancelled/completed) are left untouched. Reason: since notifications are derived live from `Offer`s (above) rather than stored, a fully-deleted offer could never produce a notification again — but the provider still needs to learn their job disappeared, distinctly from an ordinary reject. `notifications.ts` tells the two `rejected` causes apart by checking whether `offer.jobId` still resolves in the live `jobs` array: found → the existing `teklif_reddedildi`; not found → a new `NotificationType`, `hizmet_kalemi_kaldirildi` ("Hizmet Talebi Kaldırıldı" / "İlan sahibi ilgili hizmet talebini yayından kaldırdı.") — the same "disambiguate by an extra condition, not a new status" pattern `siblingClosedNotifications` already uses for `pending`.

### Turkey location data

`app/_lib/turkey-locations.ts` reads facility data (OSB/port/free-zone/depot/etc.) from a **single source**, `data/locations/locations.json` — there is no separate hand-curated facility list anywhere else in the repo. That one file mixes three kinds of records under a shared schema (`id, name, type, provinceId, districtId, aliases, active`):

1. **Pipeline-verified entries** — provinces run through `locations:import:<province>` + `locations:verify` (currently only Kocaeli, `provinceCode: "41"`), scored via real Overpass/OSM polygon verification (`scripts/locations/lib/score.mjs`: ≥80 auto-`VERIFIED`/active, 60–79 `REVIEW`/inactive, duplicates within ~walking distance merged by `lib/dedup.mjs` into one canonical record with the losers' names folded into `aliases`).
2. **Migrated legacy entries** — every other province, carried over verbatim by the one-off `scripts/locations/migrate-legacy.mjs` from the old hand-curated `app/_data/turkey/{osb,ports,free-zones,logistics-centers}.json` files (which no longer exist in the repo; that script deleted them after migrating). These are `active: true` for display purposes but have **not** been through real polygon verification — don't assume "present in `locations.json`" implies "geo-verified" for any province other than Kocaeli.
3. **Manually overridden/added entries** — `data/locations/location_manual_overrides.json`, applied by `verify.mjs` on every run, *after* step 1's pipeline scoring and scoped by `provinceId`. Three actions, keyed by `matchId` (an existing record's `id`) except `add`: `"promote"` overwrites a matched record's `name`/`district(Id)`/`officialWebsite`/`phone`/`fullAddress`/`active`/`confidenceScore`/aliases (merged, never replaced) and always sets `verificationStatus: "VERIFIED"` regardless of the `active` value passed — this is the mechanism for both activating a real facility the auto-scorer under-scored *and* deliberately deactivating one it over-scored (e.g. a shipyard wrongly caught by a "liman" keyword match); `"reject"` sets `active: false` + `verificationStatus: "REJECTED"` on a matched record, used for confirmed OSM duplicates or wrong-province/wrong-category records, never for a record that's merely a different *kind* of facility (that's a `"promote"` with `active: false` instead, so the reason is auditable and distinct from "this candidate doesn't physically exist"); `"add"` inserts a brand-new record (its own `id`, prefixed `loc-manual-`) for a real facility the Overpass query never surfaced as a candidate at all — this has turned out to be the norm rather than the exception for whole categories (OSB, free zones, TCDD logistics centers, flagship industrial plants), since OSM/Overpass frequently has no usable polygon for large single-owner sites. Every override's `manualSource` field is a required, freeform citation of the real-world source (official site, ministry registry, chamber-of-commerce listing) — treat it as mandatory, not optional, when adding a new override. The whole file is designed to survive a full pipeline re-run: `verify.mjs` is idempotent, so re-running `locations:verify` after an Overpass re-fetch re-applies every override deterministically rather than needing to be redone by hand.

Only `active === true` records are ever shown; a `districtId: null` record (district unresolved) deliberately never matches any district filter rather than risk being shown under the wrong one. Lookups are always **province + district + facility type together** via `getFacilitiesByProvinceDistrictAndType(provinceId, districtId, type)` — there's no province-only or name-only lookup. `app/_data/turkey/{provinces,districts}.json` (81/81 provinces) are the unrelated, complete, static province/district reference and are not part of this pipeline.

### Site-wide access gate

`proxy.ts` (project root — Next.js 16 renamed `middleware.ts` to `proxy.ts`; per AGENTS.md, check `node_modules/next/dist/docs/` before assuming training-data conventions here) sits in front of every route (pages *and* `/api/*`) and redirects (pages) or 401s (`/api/*`) any request without a valid `malsevk_site_access` cookie — a temporary, site-wide password wall for the Vercel Hobby deployment being publicly reachable, **unrelated to and running before** the app's own `users.ts`/`session.ts` login system covered above. Active only when `NODE_ENV === "production"` (same convention as `DEV_ACCOUNTS`/`demo-veri-sifirla`) — `npm run dev` is never gated, but `npm run build && npm start` now behaves like Vercel and needs `MALSEVK_SITE_PASSWORD` set locally too. `app/_lib/site-access.ts#computeSiteAccessToken` derives a one-way SHA-256 token from the password for the cookie value (never the plaintext password itself), validated with a timing-safe comparison; if `MALSEVK_SITE_PASSWORD` is unset, no token can ever validate — fail-closed by construction, not a separate check. `app/site-erisim/` (the only route besides `_next`/`favicon.ico` excluded from the gate) is a Server Action (`verifySiteAccess`) with a fixed ~1s delay plus a best-effort per-IP in-memory counter against brute-forcing; also handles logout (`clearSiteAccess`, clears the cookie).

### Legal documents (Gizlilik Politikası / Kullanım Koşulları / KVKK)

`app/_lib/legal-documents.ts` is the single central registry for the three legal texts — each `LegalDocumentMeta` (`id`, `title`, `version`, `effectiveDate`, `lastUpdatedDate`, `routePath`, `sections`) is the **only** place version/date metadata is defined; nothing else (modal, standalone page, footer) hardcodes a version or date. Publishing a new revision means editing only this registry (bump `version`/`lastUpdatedDate`) plus the corresponding content file — no other file changes. The actual legal text is data, not JSX: `legal-content-privacy.ts`/`legal-content-terms.ts`/`legal-content-kvkk.ts` each export a `LegalDocumentSection[]` (`heading`, `paragraphs`, optional `list`), kept as three separate documents deliberately — Gizlilik Politikası is the broad, general-audience policy while KVKK Aydınlatma Metni follows the narrower, mandatory Article-10 disclosure format; they overlap in subject matter but not in legal function. Bracketed placeholders (`[Şirket Unvanı]`, `[Şirket Adresi]`, `[MERSİS Numarası]`, `[Başvuru E-posta Adresi]`) mark the corporate-identity fields not present anywhere in the codebase — must be filled in (and the text given a final legal review) before this goes to production.
- **Rendering**: `legal-document-content.tsx` (title + Sürüm/Yürürlük Tarihi/Son Güncelleme meta row + sections) is the single content renderer, used identically by `legal-document-modal.tsx` and by each of the three standalone pages (`app/gizlilik-politikasi`, `app/kullanim-kosullari`, `app/kvkk-aydinlatma-metni`) — text is never duplicated between the modal and page paths.
- **Two access paths, same content, deliberately different chrome**: the standalone pages exist so a direct URL/new-tab/right-click/middle-click never 404s (SEO, email signatures, etc.) and render the content plainly (no accept UI, no modal at all — they call `legal-document-content.tsx` directly). `site-footer.tsx`'s "Yasal" links keep a real `href` to that same route for exactly those non-plain-left-click cases, but a plain left click (`event.button === 0` with no modifier key) calls `preventDefault()` and opens `legal-document-modal.tsx` instead — per-task requirement that footer clicks must not navigate. `DialogShell` (`dialog-shell.tsx`) gained an opt-in `size` prop (`"md"` default, unchanged — still what `job-rating-modal.tsx`/`offer-outcome-panel.tsx` use; `"lg"` is `max-w-3xl max-h-[90vh] overflow-y-auto`, used only by the legal modal) rather than a second modal shell, so ESC/backdrop-click/focus behavior stays identical across every modal in the app.
- **`LegalDocumentModal`'s required `mode: "readonly" | "consent"` prop is what actually separates the two access paths' UI, not a second component** — `site-footer.tsx` always passes `mode="readonly"` (the "Okudum, anladım." checkbox and "Onaylıyorum" button are not rendered at all; only "Kapat" remains, so opening a legal document from the footer — logged in or not — can never write a consent record), while `login-form.tsx` always passes `mode="consent"` (the original checkbox-gates-button behavior, unchanged). Both modes render the exact same `LegalDocumentContent` and the exact same `DialogShell`/`"lg"` chrome — only the trailing action row differs — so there is still only one modal component and one copy of the legal text; a third caller would have to explicitly pick one of the two modes, there's no default.
- **Consent recording is Supabase-shaped but localStorage-backed today**: `legal-consent.ts#LegalConsentRecord` (`documentId`, `version`, `acceptedAt`, `userId`, `ipAddress`, `deviceInfo`) is designed to map 1:1 onto a future `legal_consents` table — `ipAddress`/`deviceInfo` are permanent `null` placeholders (no server-side request context exists to fill them; see "No real backend"), and `userId` is `null` for anonymous acceptance or the real `StoredUser.id` when known. `recordLegalConsent(documentId, userId?)` always reads the **current** version from the registry (never passed in by the caller), so a version bump automatically applies to the next consent without any call-site change. In `mode: "consent"`, checking "Okudum, anladım." is required before "Onaylıyorum" enables; only "Onaylıyorum" records a consent — ESC/backdrop-click/"Kapat" all close without writing anything, identically in both modes.
- **Registration form uses one combined checkbox, not three**: `login-form.tsx` replaced the old separate `kvkkAccepted`/`termsAccepted` checkboxes with a single `legalConsentAccepted` field (`register-form-validation.ts`'s `RegisterFormErrors.legalConsent` is now the one error key) — the sentence embeds all three document titles as independent `LegalDocumentInlineTrigger` buttons, each opening its own modal via `event.stopPropagation()` (critical: without it, a click on the nested button would bubble to the wrapping `<label>` and toggle the outer checkbox, since the button lives *inside* that label). Checking the outer box directly (without ever opening a modal) is sufficient to register — the modals are for optional reading, not a forced gate. On successful `registerUser`, `recordConsentForAllLegalDocuments(result.user.id)` writes three independent consent records (one per document, same timestamp) from that single checkbox action, satisfying "each text can have its own consent record" without requiring three separate UI confirmations at signup.

### Database scaffold

`app/_lib/db.ts` (lazy Neon client via `DATABASE_URL`) and `drizzle.config.ts` exist but are **not wired into any business logic** — their only consumer is `app/api/health/route.ts`, which runs `SELECT 1` and returns 503 if it fails or `DATABASE_URL` is unset. No `db/schema.ts` exists yet and no migrations have been generated. Every real feature still reads/writes `localStorage` exclusively (see "No real backend" above) — don't assume this scaffold means any given feature is backed by a real database.
